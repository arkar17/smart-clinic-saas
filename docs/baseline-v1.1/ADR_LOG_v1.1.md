## ADR-001 Modular monolith in a pnpm workspace monorepo
- **Context:** SRS 4.5 mandates a modular monolith; budget is small; React web, Express API and worker share contracts and domain types.
- **Decision:** One repository with pnpm workspaces: `apps/web`, `apps/api` (HTTP entry `server.ts`, worker entry `worker.ts`), `packages/contracts`, `packages/config`. API code is split into domain modules (identity, platform, clinic, scheduling, booking, patients, queue, reporting, audit) plus infrastructure (realtime, jobs, db, http). Modules expose a public `index.ts`; an ESLint import-boundary rule forbids deep imports (NFR-MNT-001).
- **Alternatives:** Microservices (rejected: cost, distributed transactions break the atomic booking/queue invariants); single package without boundaries (rejected: fails NFR-MNT-001).
- **Consequences:** One deployable image, one database transaction can span booking + queue + audit + outbox. `patients` and `realtime` are additional modules beyond the SRS list — consistent with the intent of NFR-MNT-001.
- **Budget:** Negligible.

## ADR-002 Shared Zod contracts package
- **Context:** FR-SEC-008 and NFR-MNT-002 require shared validation.
- **Decision:** `packages/contracts` holds Zod schemas for every request/response, error envelope, enum and SSE payload. Schemas are `.strict()` (unknown fields rejected). The API validates input and (in tests) output; the web app uses the same schemas for forms and response parsing. No OpenAPI generator in MVP.
- **Alternatives:** OpenAPI-first (more tooling, more credits); tRPC (couples transport and hides REST inventory required by the brief).
- **Consequences:** Single source of truth; contract tests are cheap.
- **Budget:** Negligible.

## ADR-003 Server-side sessions with opaque cookie
- **Context:** FR-SEC-002 requires idle/absolute timeouts and immediate revocation (FR-STF-003: within 60 s).
- **Decision:** 256-bit random cookie `sc_sid` (HttpOnly, Secure, SameSite=Lax, Path=/). Only SHA-256 of the value is stored (`session.id_hash`). Each request loads the session, user and membership; `last_seen_at` written at most once per minute. CSRF: synchroniser token derived from `session.csrf_secret`, sent in `X-CSRF-Token`, plus Origin check (FR-SEC-009). Sessions are rotated on login and password change.
- **Alternatives:** JWT (rejected: revocation and role change need server state anyway); express-session default store (rejected: stores raw IDs).
- **Consequences:** One indexed lookup per staff request; revocation is immediate.
- **Amendment (rev B):** The session also stores the selected membership (`active_clinic_id`, `active_member_id`) with a composite FK that includes `user_id`; switching clinic rotates the CSRF secret (ADR-034).
- **Budget:** Low.

## ADR-004 Tenant isolation without RLS in MVP
- **Context:** Critical rules 1–2; OQ-015 leaves RLS optional.
- **Decision:** (1) `clinic_id` NOT NULL on every tenant table; (2) every parent has `UNIQUE (clinic_id, id)` and every child references it through a composite FK `(clinic_id, parent_id)`, making cross-clinic references impossible at the database level; (3) clinic context comes only from session membership, slug or token hash; (4) repositories require a `ClinicContext` argument and always filter by it; (5) foreign IDs return 404; (6) automated isolation suite (TC-SEC-001/-002/-007).
- **Alternatives:** PostgreSQL RLS with `SET app.clinic_id` per transaction (stronger, but Prisma connection pooling and interactive transactions complicate it; deferred unless OQ-015 says otherwise).
- **Consequences:** A developer bug that forgets a filter is caught by tests, not by the database. Composite FKs still block cross-tenant writes. Residual risk accepted by D-11 and documented in SRS 14.2.
- **Amendment (rev B):** (1) now reads: `clinic_member` is unique per (clinic_id, user_id); the clinic context comes from the session’s selected membership, re-validated on every request (ADR-034).
- **Budget:** Low (composite FKs are declared in Prisma with `@relation(fields: [clinicId, doctorId], references: [clinicId, id])`).

## ADR-005 Key strategy
- **Decision:** `uuid` with `gen_random_uuid()` for entities; `bigint GENERATED ALWAYS AS IDENTITY` for `audit_log` and `clinic_event` (ordering and Last-Event-ID). IDs are opaque and never sequential in public URLs.
- **Alternatives:** UUIDv7 (better locality; not needed at MVP scale).
- **Budget:** Negligible.

## ADR-006 Appointment overlap by exclusion constraint
- **Context:** Critical rule 3; SRS 13.2; TC-APT-006.
- **Decision:** `EXCLUDE USING gist (doctor_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status IN ('PENDING','CONFIRMED','CHECKED_IN','COMPLETED'))` with `btree_gist`. Because a constraint predicate cannot use `now()`, every hold/create/reschedule transaction first runs `UPDATE appointment SET status='EXPIRED', expired_at=now() WHERE doctor_id=$1 AND status='PENDING' AND hold_expires_at <= now() AND tstzrange(start_at,end_at) && $range`. Violation SQLSTATE 23P01 maps to `409 SLOT_UNAVAILABLE`. Half-open ranges allow back-to-back bookings (BR-053).
- **Alternatives:** SERIALIZABLE isolation with retry (works but retries are harder to test); advisory lock per doctor-day (relies on every code path remembering to lock).
- **Consequences:** Correct under any concurrency, including staff vs public races. Raw SQL migration (ADR-019).
- **Budget:** Low.

## ADR-007 Rescheduling as one conditional UPDATE
- **Context:** Critical rule 4; FR-APT-011 ("new slot acquired before old released").
- **Decision:** `UPDATE appointment SET doctor_id, start_at, end_at, service_date, version=version+1 WHERE id AND clinic_id AND status='CONFIRMED' AND version=$v`. The exclusion constraint evaluates the new range against other rows; on violation the transaction rolls back and the original row is untouched. Reference and access token are unchanged; the BOOKING token's `expires_at` is recomputed in the same transaction.
- **Alternatives:** Cancel + create (breaks reference continuity and has a window where both or neither exist).
- **Budget:** Negligible.

## ADR-008 Queue counter row as serialisation point
- **Context:** Critical rule 5; FR-QUE-004; BR-062; FR-CLN-007.
- **Decision:** `queue_counter (clinic_id, service_date)` holds `last_token`, `walk_in_count`, `walk_in_paused`. Every queue-entry creation (QR walk-in, staff walk-in, check-in) runs: upsert row → `SELECT … FOR UPDATE` → checks → `UPDATE … SET last_token = last_token + 1 [, walk_in_count = walk_in_count + 1] RETURNING last_token` → insert entry. Rollback undoes the increment, so tokens are gapless. `UNIQUE (clinic_id, service_date, token_number)` and FK `(clinic_id, service_date) → queue_counter` are backstops.
- **Alternatives:** PostgreSQL SEQUENCE per clinic-day (unbounded objects, gaps on rollback); MAX()+1 (races).
- **Consequences:** Registrations for one clinic-day are serialised (milliseconds each) — acceptable for ≤ 500 walk-ins/day.
- **Budget:** Negligible.

## ADR-009 Duplicate-phone walk-in rule under the counter lock
- **Context:** SRS 13.2 describes a partial unique index on (clinic, date, phone) for all non-terminal entries. But FR-QUE-018 applies the rule to **public** registration only, and OQ-011's default lets reception register family members sharing a phone as staff walk-ins; a scheduled check-in for the same phone is also legitimate. A global unique index would block these. Phone also lives on `patient`, not on `queue_entry`.
- **Decision:** Inside the QR walk-in transaction, after locking the counter row, `SELECT 1 FROM queue_entry qe JOIN patient p ON (p.clinic_id, p.id) = (qe.clinic_id, qe.patient_id) WHERE qe.clinic_id=$c AND qe.service_date=$d AND p.phone_e164=$phone AND qe.status IN ('REGISTERED','WAITING','CALLED','IN_CONSULTATION')`. Because all creations for that clinic-day hold the same row lock, the check-then-insert is race-free. Staff walk-ins and check-ins skip the check.
- **Alternatives:** Partial unique index limited to `source='QR_WALK_IN'` (would still allow a QR registration while a staff entry is active, violating FR-QUE-018).
- **Consequences:** Reported as contradiction C-02 in the architecture document; behaviour matches FR-QUE-018 + OQ-011 default.
- **Budget:** Negligible.

## ADR-010 Private access tokens
- **Context:** Critical rule 7; BR-022/023; FR-SEC-006.
- **Decision:** 32 bytes from `crypto.randomBytes`, base64url (43 chars). Store `sha256(token)` in `public_access_token.token_hash` (unique). Lookup by hash (equality on a hash of a high-entropy secret is not timing-sensitive; `timingSafeEqual` is still used when comparing reservation secrets). Web routes keep the SRS form `/c/<slug>/b/<token>` and `/c/<slug>/q/<token>`; the SPA reads the token from the path and calls the API with header `X-Access-Token`, so API access logs never contain it; the static web server's access log redacts `/b/*` and `/q/*`. Token pages set `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex`. Expiry per BR-023, recomputed on reschedule/cancel; revocation sets `revoked_at`. Invalid, expired, revoked and other-clinic tokens all return the same 404.
- **Alternatives:** Signed JWT links (cannot be revoked without state, longer URLs).
- **Budget:** Low.

## ADR-011 Idempotency with encrypted response bodies
- **Context:** SRS 13.3 requires an identical replay response; the confirm and walk-in responses contain the raw private link, but critical rule 7 forbids storing raw secrets.
- **Decision:** `idempotency_record.response_body_enc` is AES-256-GCM encrypted with `IDEMPOTENCY_ENC_KEY` (env), random 96-bit nonce, AAD = clinic_id|endpoint|key. Records expire after 24 h and are purged hourly. A first request inserts `IN_PROGRESS` (PK conflict → `409 REQUEST_IN_PROGRESS` or replay); the record is completed in the same transaction as the business write.
- **Alternatives:** Re-issue a new token on replay (responses differ, breaks TC-APT-010); store raw response (violates rule 7).
- **Consequences:** A database-only leak cannot reveal tokens; leak of DB **and** key for the last 24 h could. Documented residual risk.
- **Budget:** Low.

## ADR-012 Transactional outbox + pg_notify + in-process SSE hub
- **Context:** SRS 13.6 (publish after commit, monotonic IDs); the worker (separate process) also changes queue state (day close, expiry).
- **Decision:** Each state-changing transaction inserts `clinic_event` rows and calls `pg_notify('clinic_event', id::text)`. PostgreSQL delivers NOTIFY only on commit. The API holds one dedicated `pg` LISTEN connection, loads the event, and the in-memory hub routes it (ADR-026 rules). Events are purged after 24 h. On LISTEN reconnect the hub broadcasts `resync` to every stream.
- **Alternatives:** Post-commit hook in API only (misses worker changes); Redis pub/sub (extra container).
- **Consequences:** Works across processes and later across API instances. Event IDs are globally increasing, therefore increasing per clinic.
- **Budget:** Low–Medium.

## ADR-013 Separate worker process
- **Context:** Requested "small background notification worker"; FR-APT-014 (expiry ≥ every minute), FR-QUE-016, FR-APT-013 (day close), retention purges.
- **Decision:** `apps/api/src/worker.ts` runs in its own Compose service with the same image. Jobs: hold-expiry sweep (60 s), day close per clinic (every 5 min, closes all non-terminal records with `service_date < clinic-local today`), notification-job poll (10 s, `FOR UPDATE SKIP LOCKED`, lease 60 s, exponential backoff, max 5 attempts), purge (hourly: idempotency, events, expired sessions, IP hashes > 30 days). All jobs are idempotent conditional updates (NFR-REL-002); correctness never depends on them running on time (query-time expiry).
- **Alternatives:** In-process timers in the API (fewer containers, but long jobs share the event loop with SSE; kept as fallback via `RUN_WORKER_IN_PROCESS=true` for the cheapest hosting).
- **Budget:** Low.

## ADR-014 NotificationJob limited to in-app staff alerts
- **Context:** The architecture brief requests a notification worker and a NotificationJob entity. The SRS excludes SMS/WhatsApp/email to patients (4.2, 18) and states no email is sent (A-004). An outbound notification channel would change approved scope.
- **Decision:** `notification_job` carries only `SCHEDULE_CONFLICTS_DETECTED` (enqueued after hours/closure/schedule/exception changes; worker counts affected future appointments and emits a `staff.alert` event to CA/RC) and `DOCTOR_UNAVAILABLE_REASSIGN` (after FR-DOC-006; lists WAITING entries to reassign). Payloads contain IDs only. No channel column exists; adding external delivery requires a new ADR and SRS change.
- **Alternatives:** Omit the entity (rejected: requested); model SMS/email channels "for later" (rejected: scope creep, invites accidental use).
- **Consequences:** Reported as contradiction C-01 with this resolution.
- **Budget:** Low.

## ADR-015 Time model
- **Context:** Critical rule 11; SRS 12.1; NFR-DAT-001.
- **Decision:** All instants `timestamptz` (UTC). Weekly rules stored as `weekday` (ISO 1–7) + `start_min`/`end_min` local minutes. Dates that matter to the clinic stored as `date` in clinic-local terms (`service_date`, `exception_date`, closure dates). Conversion uses Luxon with the clinic's IANA zone; a nonexistent local time (DST gap) is skipped, an ambiguous one uses the earlier offset. All "now" values come from an injectable `Clock` (NFR-TST-003). Timezone is immutable after activation (A-017, trigger).
- **Alternatives:** Temporal polyfill (heavier, less mature tooling); date-fns-tz (adequate; Luxon chosen for explicit zone handling).
- **Budget:** Negligible.

## ADR-016 Status-transition enforcement in three layers
- **Context:** Critical rule 12; SRS 9.
- **Decision:** (1) Pure domain functions `appointmentTransition(from, action, ctx)` and `queueTransition(...)` encode SRS tables AT-01..11 and QT-01..14 with preconditions; 100 % transition coverage tests. (2) Persistence uses conditional `UPDATE … WHERE status=:from AND version=:v`; zero rows → re-read → `409 INVALID_TRANSITION` or `409 VERSION_CONFLICT`. (3) `BEFORE UPDATE OF status` triggers `appointment_status_guard` / `queue_status_guard` reject any (old, new) pair not in the whitelist (defence in depth against code paths that bypass the domain layer, including scripts).
- **Alternatives:** Application only (single layer); full DB state machine with preconditions in PL/pgSQL (duplicated business logic).
- **Budget:** Low.

## ADR-017 Rate limiting
- **Context:** Critical rule 8; FR-SEC-007; SRS 14.5.
- **Decision:** `rate-limiter-flexible` memory store keyed by HMAC(IP) and by clinic, applied per endpoint group with SRS 14.5 limits; 429 + `Retry-After`. Durable limits that protect inventory live in the database: one PENDING hold per browser (`UNIQUE (clinic_id, hold_client_hash) WHERE status='PENDING'`), ≤ 5 active holds per IP per clinic (counted in the hold transaction), MAX_ACTIVE_BOOKINGS per phone, walk-in capacity, duplicate phone. Trust proxy is configured to the single reverse proxy hop.
- **Alternatives:** PostgreSQL-backed limiter (cost per request); Redis (extra container).
- **Consequences:** Memory limits reset on restart and are per-instance — acceptable for single-instance MVP; documented.
- **Budget:** Negligible.

## ADR-018 Argon2id
- **Decision:** `argon2` (Node) with Argon2id, memoryCost 19 MiB, timeCost 2, parallelism 1 (OWASP minimum); bcrypt cost 12 only if the native module cannot build. Common-password list bundled (BR-080).
- **Budget:** Negligible.

## ADR-019 Migrations with hand-written SQL
- **Context:** Prisma schema cannot express exclusion constraints, partial unique indexes, CHECK constraints, generated columns, triggers or role privileges.
- **Decision:** `prisma migrate dev --create-only` produces each migration; the developer appends SQL for those objects in the same migration file. Migrations are never edited after merge. A `db:verify` script (run in CI after `migrate deploy`) queries `pg_constraint`, `pg_indexes`, `pg_trigger` and `information_schema.role_table_grants` and fails if any required object is missing — guarding against Prisma drift handling dropping them. Extensions created in migration 0001.
- **Budget:** Low.

## ADR-020 Clinic settings as columns
- **Decision:** Booking and walk-in settings are typed columns on `clinic` with CHECK ranges, versioned by `clinic.version`.
- **Alternatives:** `clinic_settings` 1:1 table or JSONB (weaker validation).
- **Budget:** Negligible.

## ADR-021 Hours as interval rows
- **Context:** SRS models open/close + 0–3 breaks per day (BR-040/041).
- **Decision:** Store the resulting open intervals (≤ 4 per weekday); breaks are gaps. The UI edits "open, close, breaks" and the API converts both ways. Exclusion constraints prevent overlapping intervals. Same model for doctor availability.
- **Alternatives:** Columns open/close + break table (more joins, same expressiveness).
- **Budget:** Negligible.

## ADR-022 Per-doctor walk-in cap not modelled
- **Context:** FR-CLN-006 lists an optional per-doctor daily cap as COULD.
- **Decision (D-05):** Not in MVP schema; also covers clinic logo upload and portal visit counters. It can be added later as `doctor.walkin_daily_cap` + a per-doctor count derived under the existing counter lock — additive migration, no redesign.
- **Budget:** Saves Low.

## ADR-023 Anonymous hold cookie
- **Context:** BR-054 limits one active hold per "browser session", but public users are anonymous.
- **Decision:** On first hold, the API sets `sc_hold` (random 128-bit, HttpOnly, Secure, SameSite=Strict, Path=/api/public, 1 h). Its SHA-256 is stored in `appointment.hold_client_hash` while PENDING. Creating a new hold cancels the previous one from the same cookie (AT-04) in the same transaction. The cookie is strictly necessary for the booking function and carries no tracking.
- **Budget:** Negligible.

## ADR-024 Display key as DISPLAY-purpose access token
- **Context:** A-025.
- **Decision:** Staff create a display key (`purpose='DISPLAY'`, label, no expiry, revocable). The display URL is `/display#k=<key>`; the fragment is never sent to servers; the page sends `X-Display-Key`. Revocation closes open display streams.
- **Budget:** Negligible (no new table).

## ADR-025 Actor references via clinic_member
- **Decision:** `created_by_member_id`, `updated_by_member_id`, `paused_by_member_id` reference `clinic_member` through composite FKs, so attribution cannot cross tenants. With multi-clinic accounts this also records *which* membership acted. `audit_log.actor_user_id` references `app_user` because platform actions have no clinic.
- **Budget:** Negligible.

## ADR-026 PII-free events
- **Context:** Critical rule 9; SRS 13.6 says staff payloads may include names.
- **Decision:** `clinic_event.payload` holds only IDs, status, token number, doctor ID, version and counters. Routing: CA/RC streams receive all events of their clinic; DR streams receive events where `doctor_id` = own doctor; public entry streams receive a server-computed personal status (own status, people ahead, now-serving token) recomputed when any event for their doctor arrives (debounced 250 ms); display streams receive a recomputed board (tokens only). Staff UIs refetch the changed entry by ID over REST to show names.
- **Alternatives:** Names in events (simpler UI, but the outbox table would hold PII and mis-routing would leak it).
- **Consequences:** One extra small REST call per change on staff screens. Reported as interpretation note C-05.
- **Budget:** Negligible.

## ADR-027 fetch-based SSE client
- **Context:** Native `EventSource` cannot send headers, so access tokens would have to go in the URL (logged) and Last-Event-ID handling is opaque.
- **Decision:** Use `@microsoft/fetch-event-source` on the client; server emits standard `text/event-stream` with `id:`, `event:`, `data:` and a 25 s heartbeat comment. Staff streams use the session cookie plus CSRF-free GET; public streams use `X-Access-Token`; display streams use `X-Display-Key`.
- **Budget:** Negligible.

## ADR-028 Queue order at confirmed physical arrival (business)
- **Decision:** Implements A-012/BR-060: walk-in `sort_time = arrived_at`; scheduled `sort_time = max(arrived_at, appointment start)`; tie-break token number. REGISTERED entries have no `sort_time` and are excluded from the line.
- **Status:** Accepted — confirmed in revision B (D-14, formerly OQ-003); the rule is isolated in one domain function.

## ADR-029 Single daily token sequence (business)
- **Decision:** Implements A-011/BR-021: one numeric sequence per clinic-day for all sources and doctors. Changing to per-doctor sequences later would add `doctor_id` to the counter key.
- **Status:** Accepted — confirmed in revision B (D-14, formerly OQ-008).

## ADR-030 Day-close rules (business)
- **Decision:** Implements A-013/A-021/A-022 and FR-QUE-016: for each clinic, records with `service_date < local today` are finalised: REGISTERED → EXPIRED; WAITING/CALLED → CANCELLED (SYSTEM_DAY_CLOSE); IN_CONSULTATION → COMPLETED auto_closed; CONFIRMED appointments → NO_SHOW; linked appointments follow AT-10/AT-11. Runs every 5 minutes (idempotent), so it happens within minutes after local midnight.
- **Status:** Accepted — confirmed in revision B (D-14, formerly OQ-005 and OQ-006).

## ADR-031 Unverified phone numbers (business)
- **Decision:** As SRS BR-032 — phones are validated and normalised (libphonenumber-js, `isValid()`), not verified. Abuse controls: rate limits, per-phone limits, duplicate rule, staff arrival confirmation, EXPIRED-rate metric.

## ADR-032 Conflicts computed on read
- **Decision:** `GET /api/appointments/conflicts` evaluates future CONFIRMED appointments against current rules (same availability engine). The worker only raises a staff alert (ADR-014) so that staff notice conflicts without polling. No persisted conflict table.
- **Budget:** Saves Low.

## ADR-033 Error code extensions
- **Decision:** The SRS 13.5 set is kept unchanged and extended with: `CSRF_INVALID` (403), `PASSWORD_CHANGE_REQUIRED` (403), `ACCOUNT_LOCKED` (429), `CLINIC_READ_ONLY` (403), `SETUP_INCOMPLETE` (409), `LAST_CLINIC_ADMIN` (409), `OVERRIDE_REASON_REQUIRED` (409), `CANCELLATION_CUTOFF_PASSED` (409), `RECALL_LIMIT_REACHED` (409), `DOCTOR_NOT_ELIGIBLE` (409), `SERVICE_NOT_BOOKABLE` (409). Each maps to an existing SRS rule; none changes behaviour.
- **Consequences:** Reported as C-06 so the SRS table can be updated in the next revision.

## ADR-034 Multi-clinic staff membership with server-side selected clinic
- **Context:** The approved product lets one staff person work for several independent clinics. Revision A wrongly enforced one clinic per user (`UNIQUE (user_id)`). Review item 1 / D-01.
- **Decision:** `app_user` is a global account; `clinic_member` holds roles and activation per clinic with `UNIQUE (clinic_id, user_id)`. A session stores one selected membership; `POST /api/auth/select-clinic` is the only way to set it and re-validates an active membership of the session's own user in an accessible clinic. A composite FK `(active_clinic_id, active_member_id, user_id) → clinic_member (clinic_id, id, user_id)` makes it impossible for a session to reference another user's membership. Every request re-loads the membership (active, clinic accessible, account active); permissions come from that membership only. Doctor profiles link to memberships, so a person can have different doctor profiles and roles in different clinics. Membership deactivation affects one clinic; global deactivation is a Platform Administrator action. Platform administrator accounts hold no memberships.
- **Alternatives:** Separate accounts per clinic (rejected by the Product Owner); clinic chosen per request via header or path (rejected: the client would choose its tenant).
- **Consequences:** One extra indexed lookup per request; streams are bound to the selected clinic; tests TC-STF-004/005/006, TC-DOC-004, TC-SEC-017.
- **Budget:** Low (three session columns, one endpoint, a clinic switcher, tests) — absorbed in SC-1.

## ADR-035 Global-account administration boundaries
- **Context:** With shared accounts, a Clinic Admin in clinic A could reset the password of someone who also works in clinic B and so reach clinic B.
- **Decision:** BR-084: a Clinic Admin may reset the password or change the login email of an account only if it has no membership in another clinic. Otherwise only the account owner or the Platform Administrator may. Adding an existing account by email creates a membership without showing or changing its password. Clinic Admins never see other memberships of an account.
- **Consequences:** Adding an existing email reveals that an account exists (staff-facing only, low risk, accepted).
- **Budget:** Negligible.

## ADR-036 X-Clinic-Id consistency header
- **Context:** A user may have two tabs open in different clinics; a switch in one tab changes the session for both.
- **Decision:** Every staff request sends `X-Clinic-Id` with the clinic the screen was loaded for. A mismatch with the session's selection returns `409 CLINIC_CONTEXT_MISMATCH` and the UI reloads. The header is never used to select data or permissions.
- **Budget:** Negligible.

## ADR-037 Receptionist no-phone exception
- **Context:** Review item 3 / D-12: public flows must always require name and phone; patients without any phone still need to be served at the desk.
- **Decision:** `POST /api/queue/walk-ins` accepts `noPhoneReason` (Receptionist, Clinic Admin) instead of a phone. The patient record stores `no_phone_reason`, has no phone, is never matched, and the entry gets no private link. Public endpoints reject any bypass field (strict schemas). Requirement FR-QUE-020 (SHOULD).
- **Budget:** Negligible; first SC-3 deferral candidate after the display board.

## ADR-038 CI from SC-1, local release, disposable load-test database
- **Decision:** D-08: a minimal GitHub Actions workflow (install, lint, type-check, unit and integration tests with a PostgreSQL service) is created in SC-1 and extended in SC-5. D-10: the release is a local Docker release; live hosting needs separate approval. D-09: load tests use separately generated fictional data in an approved, disposable database.
- **Budget:** CI ≈ $0.30 inside the SC-1 cap; no paid infrastructure.
